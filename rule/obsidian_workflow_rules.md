# Obsidian Workflow Rules

## 규칙 개요

이 문서는 Claude Code가 중요한 작업을 수행할 때 Obsidian vault에 체계적으로 기록하는 방법을 정의합니다.

**적용 범위**: 사용자가 "obsidian" 또는 "옵시디언" 키워드를 명시적으로 언급한 작업에만 적용

## 활성화 조건

### 🚨 TRIGGER Keyword

이 워크플로우는 사용자의 요청에 다음 키워드가 포함될 때만 활성화됩니다:
- "obsidian"
- "옵시디언"

**예시**:
```
✅ "obsidian을 사용해서 API 문서 생성 규칙을 만들어줘"
✅ "옵시디언으로 계획 세워서 Chapter 구조 개선해"
✅ "obsidian plan-result-report 방식으로 작업해"

❌ "API 문서 생성 규칙을 만들어줘" (키워드 없음 → TodoWrite만 사용)
❌ "Chapter 구조를 개선해줘" (키워드 없음 → Obsidian 파일 생성 안 함)
```

### IMPORTANT

- 키워드가 없는 일반 작업 요청에는 TodoWrite만 사용
- Obsidian 파일을 자동으로 생성하지 마세요

## Workflow 구조

모든 중요한 작업을 3단계로 구조화하여 기록합니다:

```mermaid
graph LR
    A[Plan 작성] --> B[작업 수행]
    B --> C[Result 작성]
    C --> D[작업 완료]
    D --> E[Report 작성]
```

### 1. Plan (계획)
- **시점**: 작업 시작 전
- **목적**: 작업 목표, 구조, 단계 명확화

### 2. Result (결과)
- **시점**: 작업 수행 중 또는 직후
- **목적**: 실행 내용, 발견 사항, 진행 상황 기록

### 3. Report (보고)
- **시점**: 작업 완료 후
- **목적**: 최종 결과, 성공 기준 달성도, 개선점 정리

## 파일 경로 규칙

### 경로 형식

```
/Users/kyle/Documents/claude/{project}/{YYMM}/{DD}/{type}/{HHMM}_{task_name}_{type}.md
```

### 구성 요소

| 요소 | 설명 | 예시 |
|------|------|------|
| `{project}` | 프로젝트명 | `chalk_admin` |
| `{YYMM}` | 연월 (2자리 연도 + 2자리 월) | `2511` (2025년 11월) |
| `{DD}` | 일자 (2자리) | `08` |
| `{type}` | 단계 타입 | `plan`, `result`, `report` |
| `{HHMM}` | 시분 (24시간 형식) | `1133` (11시 33분) |
| `{task_name}` | 작업명 (snake_case) | `chapter_path_automation` |

### 예시

```
/Users/kyle/Documents/claude/chalk_admin/2511/10/plan/1430_chapter_path_automation_plan.md
/Users/kyle/Documents/claude/chalk_admin/2511/10/result/1620_chapter_path_automation_result.md
/Users/kyle/Documents/claude/chalk_admin/2511/10/report/1730_chapter_path_automation_report.md
```

### 작업명 명명 규칙

- **형식**: snake_case (소문자 + 언더스코어)
- **길이**: 2-5 단어 권장
- **명확성**: 작업 내용을 정확히 표현

**좋은 예시**:
- `chapter_path_automation`
- `api_doc_template_creation`
- `domain_package_refactoring`

**나쁜 예시**:
- `work` (너무 모호함)
- `ChapterPathAutomation` (camelCase 사용)
- `fix-bug-in-chapter-service-related-to-parent-node-path` (너무 김)

### 작성 가이드라인

1. **목표는 명확하게**
   - "개선한다" (X) → "parentNodePath를 서버에서 자동 계산하도록 개선한다" (O)
   - SMART 원칙 적용 (Specific, Measurable, Achievable, Relevant, Time-bound)

2. **문제점 분석은 구체적으로**
   - 현재 상태, 문제점, 필요한 개선을 명확히 구분
   - 각 영역별로 독립적으로 분석

3. **작업 단계는 실행 가능하게**
   - 각 단계는 독립적으로 완료 가능해야 함
   - 체크리스트 형태로 작성하여 진행 상황 추적 용이하게

4. **성공 기준은 측정 가능하게**
   - "잘 동작한다" (X) → "addChapter 호출 시 parentNodePath가 자동 계산된다" (O)
   - 각 기준은 Boolean으로 판단 가능해야 함

## FAQ

### Q1: 모든 작업을 Obsidian에 기록해야 하나요?

**A**: 아니요. "obsidian" 또는 "옵시디언" 키워드가 있는 경우에만 기록합니다. 일반 작업은 TodoWrite를 사용하세요.

### Q2: Result 파일은 언제 작성하나요?

**A**:
- Phase별 작업 완료 시
- 중요한 발견 사항이 있을 때
- 하루 이상 걸리는 작업의 경우 매일

### Q3: Plan에서 정의한 Phase가 변경되면 어떻게 하나요?

**A**: Result 파일의 "예상과 다른 점" 섹션에 기록하고, 변경된 내용을 설명하세요. Plan 파일은 수정하지 않습니다 (원본 계획 보존).

### Q4: Report는 반드시 작성해야 하나요?

**A**: 예. Report는 작업의 가치와 교훈을 정리하는 중요한 단계입니다. 다음 프로젝트의 참고 자료로 활용됩니다.

### Q5: 작업명은 어떻게 정하나요?

**A**: snake_case로 2-5 단어로 작업 내용을 명확히 표현하세요. 예: `chapter_path_automation`, `api_doc_template_creation`

### Q6: 여러 날에 걸친 작업은 어떻게 관리하나요?

**A**:
- Plan: 작업 시작일에 생성
- Result: 매일 또는 Phase 완료 시마다 생성 (날짜별로 다른 파일)
- Report: 최종 완료일에 생성

### Q7: Plan/Result/Report 파일의 버전 관리는 어떻게 하나요?

**A**:
- 같은 작업의 경우 파일명의 시간(HHMM)으로 구분
- 수정이 필요한 경우 새 파일 생성 (기존 파일은 보존)
- 파일 하단의 "버전" 필드로 버전 표시

### Q8: Result 파일이 너무 길어지면 어떻게 하나요?

**A**:
- Phase별로 별도 Result 파일 생성 가능
- 파일명에 Phase 번호 추가: `1530_api_doc_rules_result_phase1.md`
- Report에서 모든 Result 파일 참조
