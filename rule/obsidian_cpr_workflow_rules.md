# Obsidian CPR Workflow Rules (Context-Process-Result)

## 활성화 조건

### 🚨 TRIGGER Keyword
- "obsidian" 또는 "옵시디언" 키워드가 포함된 요청
- 문서화 작업 명시적 요청
- 작업 로그 작성 요청

### 📍 활성화 시점
1. 사용자가 명시적으로 "obsidian" 키워드를 언급할 때
2. 복잡한 작업의 문서화가 필요할 때
3. 작업 이력 관리가 필요한 중요 작업일 때

---

## Workflow 구조

이 룰은 **Context-Process-Result (CPR)** 3단계 워크플로우를 정의합니다.

```
0.1 Context (맥락)  → 0.2 Process (과정) → 0.3 Result (결과)
     ↓                    ↓                    ↓
  작업 배경 분석      실행 과정 기록       최종 결과 정리
```

### Phase 1: Context (맥락)
- **목적**: 작업의 배경, 요구사항, 문제점을 분석
- **작성 시점**: 작업 시작 전 또는 초기 분석 단계
- **핵심 내용**: Why? 왜 이 작업이 필요한가?

### Phase 2: Process (과정)
- **목적**: 작업 수행 과정을 단계별로 기록
- **작성 시점**: 작업 수행 중
- **핵심 내용**: How? 어떻게 수행했는가?

### Phase 3: Result (결과)
- **목적**: 작업 결과와 영향을 정리
- **작성 시점**: 작업 완료 후
- **핵심 내용**: What? 무엇을 달성했는가?

## 파일 경로 규칙

### 기본 경로 구조

**Windows 환경**:
```
C:\Users\user\Documents\Obsidian Vault\0.1 Admin\{YYYY}\{MM}월\0.{N} {Type}\{YYYY-MM-DD} {작업명}.md
```

**macOS 환경**:
```
/Users/{username}/Documents/Obsidian Vault/0.1 Admin/{YYYY}/{MM}월/0.{N} {Type}/{YYYY-MM-DD} {작업명}.md
```

### 경로 구성 요소
- `{username}`: macOS 사용자 이름 (macOS에만 해당)
- `{YYYY}`: 4자리 연도 (예: 2025)
- `{MM}월`: 2자리 월 + "월" (예: 11월)
- `0.{N} {Type}`: 단계별 폴더
  - `0.1 Context`: 배경 및 맥락 문서
  - `0.2 Process`: 과정 및 프로세스 문서
  - `0.3 Result`: 결과 및 완료 문서
- `{YYYY-MM-DD}`: 작업 날짜 (예: 2025-11-10)
- `{작업명}`: 작업을 설명하는 한글 제목

### 파일명 예시
```
2025-11-10 헌법 문서 작성 배경.md
2025-11-10 헌법 문서 작성 프로세스.md
2025-11-10 헌법 문서 작성 결과.md
```

## 실행 규칙

### 1. 문서 작성 순서

**기본 원칙**: Context → Process → Result 순서로 작성

```
Phase 1: Context (작업 시작 전)
    ↓
Phase 2: Process (작업 진행 중)
    ↓
Phase 3: Result (작업 완료 후)
```

### 2. 문서 간 연결

각 문서는 다음 단계 문서를 참조해야 함:
- Context 문서 말미: "**다음 단계**: 0.2 Process 문서 작성"
- Process 문서 말미: "**다음 단계**: 0.3 Result 문서 작성"
- Result 문서 말미: "**문서 세트 완료**: Context → Process → Result 모두 작성됨"

### 3. 작성 시점

| Phase | 작성 시점 | 필수 여부 |
|-------|-----------|-----------|
| Context | 작업 시작 전 또는 초기 분석 완료 후 | ✅ 필수 |
| Process | 작업 수행 중 (실시간 또는 직후) | ✅ 필수 |
| Result | 작업 완료 후 | ✅ 필수 |

### 4. 동시 작성 규칙

- **Context는 항상 먼저**: 작업 시작 전 반드시 작성
- **Process는 실시간 업데이트 가능**: 작업 진행하며 단계별로 작성
- **Result는 마지막**: 모든 작업 완료 후 종합 정리

## 필수 작성 대상

### 반드시 3개 문서 모두 작성해야 하는 경우

1. **복잡한 도메인 생성 작업**
   - `/create-domain` 같은 대규모 작업
   - 여러 파일이 생성/수정되는 경우

2. **중요한 변경 작업**
   - 아키텍처 변경
   - DDL 변경 및 동기화
   - 대규모 리팩토링

3. **문제 해결 작업**
   - 버그 수정
   - 성능 개선
   - 오류 대응

4. **사용자가 명시적으로 요청한 경우**
   - "로그 작성해줘"
   - "obsidian으로 기록해줘"

### Result만 작성해도 되는 경우

1. **단순 작업**
   - 단일 파일 수정
   - 간단한 설정 변경

2. **긴급 작업**
   - 빠른 핫픽스
   - 시간이 촉박한 경우

## 작성 시 주의사항

### ✅ Do's (해야 할 것)

1. **정확한 파일 경로 사용**
   - 윈도우 경로 형식 준수: `C:\Users\user\Documents\...`
   - 역슬래시(`\`) 사용

2. **일관된 날짜 형식**
   - 파일명: `YYYY-MM-DD`
   - 문서 내: `YYYY-MM-DD HH:mm`

3. **명확한 한글 작업명**
   - 작업 내용을 정확히 설명
   - 너무 길지 않게 (5-15자)

4. **구체적인 내용 작성**
   - 추상적 표현 지양
   - 구체적 사실과 증거 기반

5. **체크리스트 완성도 확인**
   - 각 phase 체크리스트 모두 확인
   - 누락 항목 최소화

### ❌ Don'ts (하지 말아야 할 것)

1. **템플릿 변수 그대로 남기기**
   - `{작업명}` 같은 플레이스홀더를 실제 값으로 대체

2. **단계 건너뛰기**
   - Context 없이 Process만 작성
   - Result 없이 작업 종료

3. **불완전한 정보**
   - "나중에 추가 예정" 같은 미완성 표현
   - 빈 섹션 그대로 두기

4. **일관성 없는 명명**
   - 세 문서의 작업명이 서로 다른 경우
   - 날짜가 일치하지 않는 경우

5. **과도한 생략**
   - 중요한 결정 과정 생략
   - 실패한 시도나 이슈 누락

## Context-Process-Result vs Plan-Result-Report 비교

### 기존 Plan-Result-Report 방식

| Phase | 초점 | 작성 시점 |
|-------|------|-----------|
| Plan | 계획 수립 | 작업 전 |
| Result | 실행 결과 | 작업 중/후 |
| Report | 종합 보고 | 작업 완료 후 |

### 새로운 Context-Process-Result 방식

| Phase | 초점 | 작성 시점 |
|-------|------|-----------|
| Context | 배경 분석 | 작업 전 |
| Process | 과정 기록 | 작업 중 |
| Result | 결과 정리 | 작업 후 |

### 주요 차이점

1. **Context vs Plan**
   - Context: "왜?"에 집중 (배경, 문제, 요구사항)
   - Plan: "무엇을?"에 집중 (할 일 목록, 계획)

2. **Process 추가**
   - 기존 방식에는 없던 중간 단계
   - 실행 과정을 실시간으로 상세 기록
   - 의사결정, 이슈, 해결 과정 문서화

3. **Result vs Report**
   - Result: 구체적 산출물과 달성도
   - Report: 종합적 평가와 보고

### 어느 방식을 사용할까?

- **CPR 방식 (이 문서)**: 실무 중심, 과정 중시, 상세 기록
- **PRR 방식 (기존)**: 계획 중심, 결과 중시, 요약 보고

→ **사용자의 실제 문서 패턴이 CPR 방식이므로 이 룰을 우선 적용**
